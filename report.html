Summary

This package tracks the enhancements made to the keyestudio ESP32-CAM Video Car sketch's web control server (app_server.h) and main sketch (4_VideoCar.ino). It began as three changes — a virtual joystick, a connection-loss failsafe with WiFi auto-reconnect, and a redesigned control page — and has since grown a browser-side computer-vision suite, an offline model cache, and three autonomous driving modes.

The first commit is the original unmodified sketch, so the diff against stock keyestudio firmware is always inspectable with git diff 3df6eee..HEAD. Every commit is self-contained and touches both source trees together, so Codes/4_VideoCar and firmware/4_videocar/src never drift apart mid-history and any commit can be checked out and built from either system.

Testing status. Everything from e47a1c5 onward has been desk-verified only — JavaScript parsed, C++ balanced, control laws and CV kernels unit-tested against synthetic inputs, and the autonomy arbiter tested for mutual exclusion. None of it has been flashed to hardware. The autonomous modes in particular should be tested on blocks, with a hand on the joystick, before being trusted on the floor.

Features added

Joystick control new endpoint

A draggable on-screen joystick sends position updates to a new GET /joystick?x=&y= endpoint. The firmware mixes throttle/steer into per-wheel PWM using the same sign convention as the existing D-pad handlers, so it drives smoothly at any angle instead of just four discrete directions, and honors the Speed slider as a PWM cap.

Connection-loss failsafe safety

Previously, if WiFi dropped or the browser tab closed mid-drive, the car kept driving indefinitely — no timeout existed anywhere in the stack. Now:

  • Every movement command stamps lastCommandMillis.
  • loop() runs every 50 ms and force-stops the motors if 500 ms pass with no fresh command.
  • The browser resends the current command every 100 ms (previously only on change), acting as a continuous heartbeat well inside that window.
  • Station-mode WiFi now uses WiFi.setAutoReconnect(true) plus an explicit retry loop.
  • The MJPEG <img> stream reloads itself on error instead of freezing forever.
  • A live connection dot polls /status every 2 s so a drop is visible, not just inferred from the car stopping.

Mission-control UI redesign visual

Replaced the stock purple-button table layout with a dark cockpit theme: monospace console type, cyan/amber/red accent system, camera-viewfinder corner brackets and a blinking “LIVE” tag around the video feed, grouped labeled panels (Drive / Manual / Systems), live numeric readouts next to every slider, and a responsive layout (previously hard-locked to 400px). Also fixed a pre-existing bug where the Speed and Trim sliders shared the same id="speed".

Browser-side vision suite perception

Seven overlays that run entirely in the phone or laptop browser against frames from the car, with no inference on the ESP32 itself: object detection and face detection (AI Vision), body pose, hand tracking, facial expression, QR/barcode reading, and licence-plate OCR. The ESP32 only ever serves JPEG frames; every model runs client-side, which is what makes any of this possible on a 240 MHz microcontroller.

Offline model cache fixes a shipped gap

Those models load from a CDN, and the car's default AP has no route to the internet — so six of the advertised features failed out of the box and the only workaround was to abandon AP mode for a router. window.fetch is now wrapped with a read-through cache in IndexedDB over a whitelist of model hosts: use a feature once with internet and its files are kept, and it works on the car's own AP from then on.

A service worker is the textbook approach here and is unavailable — service workers and the Cache API are both restricted to secure contexts, and this page is served over plain HTTP from 192.168.4.1. IndexedDB carries no such restriction. Caching happens on read rather than behind a “download all” button, because weight-shard URLs are derived from model.json at load time and aren't knowable in advance. Both script loaders moved from <script src> to fetch(), since a src attribute never reaches the shim.

Follow-me autonomous

The first feature that drives the car rather than annotating the picture. A proportional controller turns COCO-SSD's bounding box into a steer and throttle — horizontal offset from frame centre for steering, box height as a stand-in for range — and sends them to the existing /joystick endpoint, so the firmware needed no new handler and the 500 ms failsafe covers this mode for free.

Frames come from the live MJPEG <img> via drawImage() rather than a second /capture poll, which is what makes a control loop viable at all. That needs CORS on the stream, since port 81 is a separate origin from the page; if that header is ever missing the browser refuses the image outright rather than merely tainting the canvas, so the stream drops crossorigin and reconnects plain after two failures and follow-me falls back to /capture. Video always wins.

Ports guide documentation

The two-server split (control on 80, MJPEG on 81) is the least obvious thing about the project and had never been written down: the reason is that a stream response never completes, so sharing one server would let video starve the control endpoints — and a car that won't accept a stop command because it is busy sending pictures is a dangerous car. ports.html explains that, then walks through both servers from joining the WiFi to driving from a shell.

It documents every endpoint with its real value ranges, and gives the 500 ms failsafe a section of its own, since a single curl producing a half-second twitch reads as a bug until you know a command is a lease rather than an instruction. Every claim in it was cross-checked against the handlers rather than written from memory.

Build stamp diagnostics

There was no way to tell what firmware a given car was running short of reflashing it — which made “are you sure that's the current build?” unanswerable, despite the troubleshooting notes leaning on that question more than once. The control page footer, /status and the serial console at boot now all report the version, the compiler's __DATE__ __TIME__, and the git revision, the last stamped in by a PlatformIO pre-build hook.

The hook fails soft by design: no git binary, no .git directory, or a shallow checkout leaves the firmware's own nogit default in place rather than breaking the build. Arduino IDE has no pre-build hook at all, so builds from there always report nogit — an honest “unknown” being considerably better than a stale hash. An uncommitted tree is reported as -dirty and rendered in amber, since the hash alone no longer identifies the binary in that case.

The control page is also now served with Cache-Control: no-store. The page is compiled into the firmware, so a cached copy in a browser could otherwise pair an old UI with new firmware — exactly the mismatch the stamp exists to expose.

Classic CV: motion, line, colour chase no network

Three features that need no model and no internet, because they are plain pixel maths over the frame buffer. They also keep up with the video stream rather than the 0.4–2.5 Hz a neural net manages on a phone, which is what makes the two driving ones usable as control loops.

  • Motion — passive frame differencing. Subtracts the global mean shift first: the OV2640 hunts auto-exposure continuously, and without compensation every adjustment reads as full-frame motion.
  • Line — follows a dark line on a light floor or the inverse. Thresholds midway between the band's mean and its darkest pixel so it adapts to real contrast, with a minimum-contrast guard that rejects a blank floor rather than chasing sensor noise.
  • Colour chase — drives at the nearest blob of a chosen colour, matched in rg-chromaticity so a shadow across the target doesn't lose it.

Autonomy arbiter safety

With three autonomous modes plus two manual ones, something has to decide who drives. Autonomous modes are sources of setpoints, never senders: each parks a steer/throttle value and a single 100 ms loop forwards it, with priority joystick > autonomous > D-pad. Claiming the arbiter evicts the incumbent, so two controllers can never drive at once, and any manual input disarms all of them. Motion is deliberately excluded from the registry — it doesn't drive, so there's no reason to stop watching for movement because something else is steering.

This shape is a direct response to the bug in Resolved issues below: two independent senders racing each other is what broke both manual drive modes, and an autonomous sender racing a manual one would be the worse version of it.

Resolved issues

Joystick and D-pad were fighting over the control endpoint fixed

The control page ran two independent 100 ms timers — one for the keyboard/D-pad, one for the joystick — and each sent a stop whenever its own input was idle, with no awareness of the other. Dragging the joystick had the D-pad loop calling Car_stop() ten times a second underneath it, and holding the D-pad had the joystick loop doing the same.

Why it went unnoticed: motor inertia smoothed a roughly 50% duty cycle into something that felt jerky rather than broken, so it read as a tuning problem rather than a bug.

Fix: a single arbitrated loop. Whichever input is actively in use owns the car; exactly one request goes out every 100 ms either way, preserving the heartbeat the firmware failsafe depends on.

Connection-loss failsafe didn't cover turns fixed

The Left and Right commands set the motors but never updated actstate, and loop() only force-stops when actstate != stp. Starting a turn from a standstill therefore left the state at stp, so losing WiFi mid-turn left the car spinning in place indefinitely — precisely the scenario the failsafe exists to cover.

Fix: a dedicated trn state, since a turn is neither forward nor reverse. Nothing compares against a specific state, only against stp, so the change is inert apart from closing the hole.

Unbounded WiFi connect could brick the car in station mode fixed

setup() spun in while (WiFi.status() != WL_CONNECTED) with no timeout. With ap = 0 and a wrong password, an out-of-range router, or a 5 GHz-only SSID, setup() never returned: no camera server, no AP, and no way to reach the car without opening it up and attaching a serial cable.

Fix: bounded at 20 s, after which it falls through to AP mode so the car always ends up serving something.

Line follower shipped with an unstable gain fixed

The first line-following defaults were picked by eye. Simulating the closed loop — plant, firmware mixing, and a delay buffer for the camera/JPEG/WiFi/HTTP/I2C round trip — showed LINE_SPEED 42 / LINE_KP 1.5 holding together at 80 ms of latency and falling apart at realistic ones: wandering at 250 ms and driving off the line entirely by 350 ms.

The failure is characteristic of a delay-dominated loop: raising the gain made it worse. At 250 ms, KP 2.5 lost the line where KP 0.9 tracked to about a centimetre. Dead time can't be gained away, and speed is the real limiter. Defaults are now LINE_SPEED 26 / LINE_KP 0.9, which held under 1.2 cm across 80–350 ms with no loss of line anywhere in the sweep. Curve radius turned out not to be the constraint — hairpins are fine, because the arcade mixing pivots one wheel backwards.

Smaller fixes in the same pass fixed

  • lru_purge_enable was unset on both HTTP servers. The control page holds several keep-alive connections open at once, and once max_open_sockets filled, the server refused new connections and the page appeared to hang.
  • Turns hardcoded PWM 150 and ignored the Speed slider; the joystick ignored Trim entirely; and joystick_handler treated a Speed slider at zero as full speed while the D-pad treated it as stopped.
  • The unreachable RGB888 path in capture_handler and its five vendored dl_lib headers were removed (~3,100 lines).
  • A stray Chinese debug println and an unused global were dropped.

Camera init failed (0x106) under PlatformIO only fixed

After moving the build to PlatformIO, esp_camera_init() started failing with ESP_ERR_NOT_SUPPORTED (0x106) and, on marginal power supplies, a reset loop right after -- while the identical hardware kept working fine when flashed from Arduino IDE. That pointed at the build toolchain rather than the board.

Root cause: PlatformIO's generic esp32cam board definition doesn't set the BOARD_HAS_PSRAM / -mfix-esp32-psram-cache-issue build flags that Arduino IDE's Tools > PSRAM: Enabled menu sets implicitly, and the platform was left unpinned (floating on "latest" rather than a version close to whatever Arduino IDE's Boards Manager had installed).

Fix (firmware/platformio.ini): pinned platform = espressif32@6.5.0 and added -DBOARD_HAS_PSRAM / -mfix-esp32-psram-cache-issue to build_flags. Confirmed working after reflashing. Also hardened 4_VideoCar.ino independently of the toolchain fix: retries camera init at 10MHz XCLK before giving up, enables the brownout-detector workaround (was shipped commented out), and blinks a visible LED error pattern on persistent failure instead of silently returning.

Known limitations / open items

Not tested on hardware. Everything from e47a1c5 onward is desk-verified only. The autonomous modes should be run on blocks first, with a hand on the joystick.

Security, carried over from the original sketch:

  • No authentication on /control, /joystick or /status: anyone on the AP can drive the car, and every command is a GET, so a bare <img src> on any page open in a connected browser is enough. The default AP password (88888888) is also weak.
  • Access-Control-Allow-Origin: * on the control endpoints. The stream now sets it deliberately, so that the control page's canvas can read frames; the control endpoints do not need it.
  • maxconnection = 1 means a second device cannot connect at all, and an unclean disconnect can hold the slot until the AP times it out.

Architecture and performance:

  • The older vision loops still poll /capture while the MJPEG stream runs on port 81, so two tasks call esp_camera_fb_get() on one sensor. Follow-me and Classic CV avoid this by reading the stream directly; the remaining loops have not been migrated.
  • Autonomy is bounded by loop latency, not by the control law. The full camera → JPEG → WiFi → browser → HTTP → I2C round trip is on the order of a few hundred milliseconds; a real line follower uses reflectance sensors at 100+ Hz. The physics, not the code, is the ceiling.
  • Tesseract.js (Plates) loads its worker and language data from inside a Web Worker, which has its own fetch the offline cache cannot intercept. It remains internet-only.
  • The control page is ~1,900 lines of HTML/CSS/JS inside a C string literal, duplicated across two source trees kept in sync by hand. Generating index_html.h from a real .html file at build time would remove both problems.
  • preview_full.png is 2.1 MB and in git history permanently.
